# Handoff: Social Smart Calendar

Paste this whole file into Cursor's chat (Cmd-L) as the first message in a new
conversation, with your project open. It is written to be self-sufficient — you
don't need any prior context to act on it.

## The project

TanStack Start (SSR) + React + TypeScript + Tailwind, Supabase for auth/data/realtime,
`sonner` for toasts, `lucide-react` for icons. Originally generated by Lovable.

Routes: `/`, `/auth`, `/import`, `/settings`, `/messages/`, `/messages/$id`.

Two halves:
- **Calendar** (`/`, `/import`, `/settings`) — still runs on hardcoded demo data in
  `@/data/events`. Nothing persists.
- **Messaging** (`/messages/*`) — fully wired to Supabase: DMs and groups, replies,
  reactions, GIFs/stickers, read receipts, typing indicators, realtime.

Supabase tables: `profiles`, `conversations`, `conversation_members`, `messages`,
`message_reactions`, `typing_indicators`, `imported_events`, `user_preferences`.

## Ground rules

1. **Never hand-edit `src/routeTree.gen.ts`.** It's TanStack Router codegen; it
   regenerates on dev/build.
2. **After changing SQL, re-run `supabase gen types typescript`** so
   `src/integrations/supabase/types.ts` matches. Don't hand-edit that file either.
3. **Any change to an RLS policy needs a test** (see "Verification" below). Policy
   bugs in this project have already leaked entire conversation histories.
4. `tsc --noEmit` must pass before anything is considered done.
5. Don't widen scope. Fix the item asked for; flag anything else you notice.

## Part 1 — Fixes already made (apply these, don't undo them)

These files were rewritten and should be copied into place if they aren't already.
If you're re-deriving them, the exact defects were:

### 1. Conversations opened at the wrong end of history
`src/lib/messaging.ts`, `fetchConversation`. Was:
```ts
supabase.from("messages").select("*").eq("conversation_id", id).order("created_at").limit(300)
```
Ascending + `limit` returns the **oldest** 300 rows, so any conversation longer than
300 messages opened on ancient history with nothing recent visible. Must be
`.order("created_at", { ascending: false }).limit(300)` then `.reverse()`.

### 2. Typing indicators never worked
`src/hooks/useChat.ts`, typing subscription. Was:
```ts
const row = (payload.new ?? payload.eventType === "DELETE" ? payload.old : payload.new) as ...
```
`??` binds tighter than `?:`, so the ternary condition was `payload.new` itself —
always truthy on INSERT/UPDATE — and the code read `payload.old`, which is `{}` for
those events. Every typing event was silently dropped. Correct form:
```ts
const row = (payload.eventType === "DELETE" ? payload.old : payload.new) as { user_id?: string } | undefined;
```

### 3. RLS: anyone could join any conversation
The `conversation_members` INSERT policy allowed `auth.uid() = user_id` with **no
constraint on which conversation**, so any signed-in user could insert themselves
into any conversation whose UUID they knew, then read its entire history (every
SELECT policy keys off `is_conversation_member`). The self-insert branch is removed —
only the creator or an admin adds members. There is no invite flow that needs it.

### 4. RLS: `SECURITY DEFINER` helpers as a membership oracle
`is_conversation_member(conv, user)`, `is_conversation_admin`, `can_see_message` were
callable over RPC with an arbitrary `_user_id`, letting any signed-in user ask whether
someone else belonged to a given conversation. All three now require
`_user_id = auth.uid()`.

### 5. A migration that could not run
It ran `REVOKE ALL ON FUNCTION public.update_updated_at_column()` for a function
nothing ever created. `REVOKE` on a missing function aborts the whole migration. The
function is now defined (and attached to `profiles`) before the revoke.

### 6. Unread counts drifted
The inbox pulled one 400-message window across **all** conversations and counted in
JS; a busy chat pushed other chats' unread messages out of the window. Replaced with
a `conversation_overview()` RPC that counts per conversation in Postgres. The client
falls back to the old behaviour if the RPC is missing, so it works before the
migration is applied.

### 7. Realtime refetched everything, constantly
Every realtime event ran the full conversation query (conversation + members +
profiles + 300 messages + reactions); every message anywhere refetched the whole
inbox. Message, reaction and read-receipt events now apply the payload row directly
(tables are `REPLICA IDENTITY FULL`, so rows arrive complete). Only joins, leaves and
renames reload, coalesced to one call per 400 ms.

### 8. Quadratic message rendering
`/messages/$id` ran `messages.find()` twice plus `reactions.filter()` **per message** —
~900 array scans per render at 300 messages. Now indexed into `Map`s once per change.

### 9. Message actions unreachable on touch
React/reply/edit/delete were behind `opacity-0 group-hover:opacity-100`. Touch devices
have no hover, so on the mobile layout this app is built for they were keyboard-only.
Now visible by default, hover-revealed from `sm` up.

### 10. Smaller ones
- "Delete for everyone" had no confirmation — now a sonner confirm.
- Avatars had no `onError`; expired Apple/Google URLs left broken-image icons.
- `NewConversation` declared `role="dialog" aria-modal` but never moved focus in,
  never restored it, and hung Escape off a non-focusable `<div>`. Note: the Escape
  listener must be registered **once on mount behind a ref** — hanging the effect off
  the `onClose` prop re-runs it every render and steals focus mid-keystroke.
- Invite-card "Going"/"Maybe" were `<span>`s inside the card's button, so they only
  opened the detail sheet.
- Home screen hardcoded `Hey Joel` and `Tuesday, September 2` for every user.
- A failed member insert left an orphan conversation visible to nobody.
- Sticker/GIF buttons had no in-flight guard, so a double tap sent twice.

**One thing to check first:** `src/routes/index.tsx` sets RSVP with the literals
`"going"` and `"maybe"`. The `Rsvp` union lives in `@/data/events` — if it spells them
differently, `tsc` will point at the two `setRsvp` calls. Fix them to match.

## Part 2 — Work still to do, in priority order

### P0 — Verify RLS on the two non-messaging tables
`imported_events` and `user_preferences` exist in the generated types, but no
migration on hand creates policies for them. If they were created without RLS, every
user's calendar imports and settings are readable by any signed-in user.

Check in the Supabase SQL editor:
```sql
SELECT relname, relrowsecurity FROM pg_class
WHERE relname IN ('imported_events','user_preferences');

SELECT tablename, policyname, cmd, qual FROM pg_policies
WHERE tablename IN ('imported_events','user_preferences');
```
If RLS is off or policies are missing, add owner-only policies — both tables have a
`user_id` column, so `auth.uid() = user_id` for all four commands — and enable RLS.
Write the migration, don't click through the dashboard.

### P1 — The calendar half doesn't persist anything
`/` renders entirely from the `EVENTS` / `DISCOVER` / `ME` constants in
`@/data/events`, and RSVPs live in `useState`, so they reset on navigation and nobody
else sees them. `imported_events` already exists as a table.

Work: read real events from Supabase, write RSVPs to a new `event_rsvps` table
(`event_id`, `user_id`, `status`, PK on the first two, RLS: members read, owner
writes), and keep `@/data/events` only as seed/demo fallback for signed-out users.
Propose the schema before writing it.

### P2 — Dead controls
Three buttons render and do nothing:
- create-event `+` in the bottom tab bar (`src/routes/index.tsx`, `TabBar`)
- `Add to calendar` and `Save` on each Discover card

Either wire them up or remove them. A control that does nothing is worse than absent.

### P3 — Add the checks that would have caught all of this
Nothing in this repo runs typecheck, lint, or tests. Add:
- `npm run typecheck` → `tsc --noEmit`, and run it in CI on every push
- an RLS test that signs in as user A, creates a private conversation, then as user B
  attempts (a) to insert themselves into `conversation_members` for it and (b) to
  select its messages. **Both must fail.** This is the single highest-value test in
  the project.

### P4 — Smaller items
- `findDirectConversation` matches on `is_group = false` alone, so a DM that ever had
  a third member added still resolves as that pair's direct chat.
- "Seen" in a group means "at least one other person read it" (the cutoff is the max
  of others' `last_read_at`). Consider "Seen by N".
- GIFs are eight hardcoded hotlinked `media.giphy.com` URLs, with no attribution and
  no search. Giphy's API is the supported route if this becomes more than a demo.
- Message history is capped at 300 with no pagination — no way to scroll further back.
- `useInbox` subscribes to all `messages` changes unfiltered; every message the user
  can see anywhere triggers an inbox refresh.

## Verification

Run before calling anything done:

```bash
npx tsc --noEmit          # must be clean
npm run lint              # if configured
npm run dev               # then exercise the flows below
```

Manual passes that catch what unit tests here won't:
1. Open a conversation with 300+ messages — it must land on the **newest** message.
2. Type in one browser, watch a second browser signed in as another user — "X is
   typing…" must appear, and clear ~3s after you stop.
3. On a phone or with touch emulation on, long list of messages — react/reply/edit/
   delete must be reachable **without hover**.
4. Send a message and watch the network tab: one insert, no full-conversation refetch.
5. Sign in as a user who is not a member and hit `/messages/<some other conversation
   id>` — it must fail to load, not render the history.
